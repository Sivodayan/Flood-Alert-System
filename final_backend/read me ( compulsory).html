Flood Monitoring System — Backend Documentation

For the frontend . This explains what the backend does, how to talk to it, and a few bugs you should know about before building against it.

Note: this is a test project, not a production deployment. Auth, rate limiting, and strict CORS were intentionally left out for now.

1. Architecture — the three moving parts

[Ultrasonic Sensors] --POST--> [Node/Express API : 3000] --broadcasts--> [WebSocket : 3000] --> [Frontend Dashboard]
                                        |
                                        v
                                [SQLite: flood_data.db]
                                        ^
                                        |
                          [Python/FastAPI ML Service : 8001]  <-- GET /predict --  [Frontend]


- **Node/Express server (port 3000)** — `server.js`, `routes.js`, `websocket.js`, `db.js`, `sms.js`
  Handles incoming sensor data, stores it, pushes live updates over WebSocket, serves history, and sends SMS alerts.
- **Python ML service (port 8001)** — `ml_service.py`
  A **completely separate process**. It is NOT started by `server.js` — you (or whoever runs the backend) must start it manually. It reads directly from the same `flood_data.db` file and predicts when water will reach a danger threshold.
- **SQLite database** — `flood_data.db`, shared by both services.

---

## 2. How to run it (dev)

```bash
# Terminal 1 — Node API + WebSocket
node server.js          # listens on http://0.0.0.0:3000

# Terminal 2 — ML prediction service
uvicorn ml_service:app --port 8001 --reload
# Must be run from the same folder as flood_data.db, since it opens it with a relative path.

Frontend should point to:

  • REST + WebSocket: http://<host>:3000 / ws://<host>:3000
  • ML predictions: http://<host>:8001

3. REST API (port 3000)

POST /api/readings

Sensors call this to submit a new water level reading. You probably won't call this from the frontend, but it's useful for simulating sensor data while testing.

Request body:

{
  "sensor_id": "sensor_01",
  "water_level": 23.5,
  "water_rising_level": 2.1
}

What happens:

  1. Broadcasts the reading to every connected WebSocket client (see section 4).
  2. Saves sensor_id, water_level, and a server-generated recorded_at timestamp to the database.
  3. ⚠️ water_rising_level is NOT saved to the database. It only goes out over the WebSocket broadcast, so if you need historical rising-rate data later, it won't be there — only in the live feed.

Response:

{ "status": "ok" }

No validation is currently done on the body, so malformed requests won't be rejected — they'll likely just produce null/undefined values in the DB.

POST /api/alert

Triggers an SMS alert. ⚠️ Currently broken — see Known Issues #1 below before you build a "send alert" button around this.

Request body:

{
  "alert": "DANGER",
  "ETA": "15 minutes",
  "location": "Riverside Colony"
}

alert must be one of: DANGER, Warning, Early_warning, safe.

Intended behavior: | alert value | SMS sent | |---|---| | DANGER | "Please evacuate immediately .. location {location}" | | Warning | "Floodwater is expected to arrive in approximately {ETA}" | | Early_warning | (empty message — not written yet) | | safe | (empty message — not written yet) |

Phone numbers are currently hardcoded placeholders (+94xxx, +94) rather than real numbers, since real numbers weren't needed during development.

Response:

{ "status": "sent" }

GET /api/history

Returns historical readings for charting.

Query params:

  • sensor_id (string)
  • limit (number, default 30) — how many data points to return

Example: GET /api/history?sensor_id=sensor_01&limit=50

Response: array of readings, oldest → newest (good for feeding straight into a line chart):

[
  { "sensor_id": "sensor_01", "water_level": 12.3, "recorded_at": "2026-09-24T05:00:00.000Z" },
  { "sensor_id": "sensor_01", "water_level": 13.1, "recorded_at": "2026-09-24T05:05:00.000Z" }
]

GET /api/latest — currently disabled

This endpoint (get the single most recent reading for a sensor) exists in the code but is commented out. It's not available right now.

Workaround for now: call /api/history and take the last item in the array, or listen on the WebSocket for the most recent broadcast.

4. WebSocket (port 3000, same server as REST)

Connect to ws://<host>:3000. No path/namespace, no auth — just connect.

There's no client→server message handling — the server only pushes data out. The only message type it sends is reading, fired every time POST /api/readings is called:

{
  "type": "reading",
  "sensor_id": "sensor_01",
  "water_level": 23.5,
  "recorded_at": "2026-09-24T05:10:00.000Z",
  "water_rising_level": 2.1
}

This is your live-update feed for the dashboard — use it to update the current reading and rising-rate display in real time.

5. ML Prediction Service (port 8001)

A separate FastAPI service. Not proxied through the Node server — call it directly.

GET /predict?sensor_id=<id>

Looks at the last 15 readings for a sensor, fits a simple linear trend, and estimates when the water will hit the danger level (50.0 cm, hardcoded). Needs at least 5 readings to say anything useful.

Possible responses, distinguished by status:

Not enough data yet:

{ "status": "not_enough_data", "message": "Need at least 5 readings, have 2" }

Water level isn't rising:

{
  "status": "not_rising",
  "current_level": 18.2,
  "rate_cm_per_min": -0.05,
  "r_squared": 0.31
}

Already past the danger level:

{ "status": "already_danger", "current_level": 52.0 }

Rising, with an ETA to danger level:

{
  "status": "ok",
  "current_level": 34.7,
  "danger_level": 50.0,
  "rate_cm_per_min": 0.42,
  "eta_minutes": 36.4,
  "eta_timestamp": "2026-09-24T06:12:00.000Z",
  "r_squared": 0.88
}

r_squared tells you how well the readings actually fit a straight line — worth showing as a confidence indicator, since a low value means the ETA prediction isn't very reliable.

6. Database schema (for reference)

Table readings in flood_data.db:

column type notes
reading_id INTEGER PK autoincrement
sensor_id TEXT
water_level REAL
recorded_at TEXT ISO 8601 timestamp, set by server

water_rising_level is not a column — see Known Issues below.

7. Known issues

(skip below issues cause this is a test project and no need to edit the code)

  1. water_rising_level sent in /api/readings is broadcast live over WebSocket but never saved to the database — only available in real time, not historically.
  2. SMS phone numbers are hardcoded placeholders, not real numbers — SMS alerts won't reach anyone meaningful until real numbers are wired in.
  3. Early_warning and safe alerts currently send an empty SMS message — the text for these hasn't been written yet.
  4. No authentication, rate limiting, or restrictive CORS is in place. Fine for this test project, but don't carry this config into anything real.
  5. The ML service is a separate process on a separate port (8001) and must be started manually — it won't come up automatically with node server.js.

8. Quick reference

What you need Call
